# 美瞳管理 App｜项目开发提示词

> **用途：** 将本文完整提供给 AI 编程助手（如 Cursor、Claude Code、Codex
> 等），并同时附上用户提供的「美瞳管理 App 高保真原型图」。\
> **目标：** 基于 Flutter + ForUI + SQLite +
> Drift，开发一个可运行、可交互、以本地数据为核心的美瞳管理应用，而不是只生成静态
> UI。

------------------------------------------------------------------------

## 1. 你的角色与开发目标

你是一名资深 Flutter 工程师、移动端架构师和 UI
实现工程师。请根据本提示词和随附原型图，设计并实现一个完整的「美瞳管理
App」。

### 核心技术栈

-   **Flutter**：应用框架
-   **ForUI**：主要 UI 组件库
-   **SQLite**：本地关系型数据库
-   **Drift**：SQLite ORM、类型安全查询、响应式数据流和数据库迁移

### 产品定位

-   本地优先（Local-first）：美瞳、护理液、提醒配置等核心数据保存在设备本地。
-   首期只有两个底部主导航：**首页**、**我的**。
-   详情、编辑、添加、提醒设置、通知记录等作为二级页面，不增加底部 Tab。
-   UI
    以随附原型图为主要视觉参考，整体采用淡粉色、简洁、柔和、轻量的设计。
-   首期以个人使用为主，不引入账号系统、云端同步或复杂后台服务。

### 开发原则

1.  先检查当前代码仓库、Flutter 版本、`pubspec.yaml`、ForUI
    版本和已有代码，再决定如何修改。
2.  如果仓库已有项目结构、状态管理或路由方案，优先沿用，不要无理由推倒重来。
3.  如果是空项目，建立清晰、可扩展的项目结构；状态管理和路由可选用成熟方案，但不要引入不必要的依赖。
4.  ForUI 组件必须以当前项目实际安装版本的 API
    为准。先查看包文档和示例，不得虚构组件名称、参数或方法。
5.  不要只输出设计说明或伪代码；要实际创建、修改代码，并确保项目能够运行。
6.  不要把业务逻辑全部写在 Widget
    中；数据库、业务规则、通知、更新功能应分层实现。
7.  每完成一个阶段都运行格式化、静态分析、代码生成和相关测试，及时修复错误。
8.  对未明确的细节，采用合理默认值并在 README
    的「设计决策与待配置项」中说明，不要因为非关键问题中断整个开发。

## 3. 首页功能要求

首页按以下顺序组织内容，具体间距、卡片样式和图标参考原型图。

### 3.1 即将到期

展示即将到期的美瞳，按到期日期升序排列。

每项至少显示：

-   美瞳缩略图
-   品牌、名称
-   周期
-   到期日期
-   剩余天数或「今天到期」
-   状态标识

交互要求：

-   点击项目进入对应美瞳详情。
-   点击「查看全部」进入到期列表。
-   到期提醒范围读取用户设置，默认提前 3 天。
-   已过期项目应与即将到期项目区分显示，不得混淆。

### 3.2 我的美瞳

展示美瞳总数、近期添加的美瞳或缩略图预览。

点击「查看全部」或该区域，进入美瞳列表。

### 3.3 美瞳统计

显示三个统计指标：

1.  **使用中（已开封且未到期）**
2.  **未开封（包装有效期未过或尚未填写）**
3.  **已过期（根据日期计算）**

统计值必须由 Drift
查询或业务层实时计算，不要把统计数字作为独立数据写入数据库。

已丢弃的记录不计入上述三个统计。

### 3.4 美瞳列表

支持：

-   按品牌或名称搜索
-   按周期筛选
-   按状态筛选
-   按颜色方案筛选（可选）
-   默认按创建时间倒序或最近更新排序
-   点击列表项进入详情
-   右下角悬浮「+」按钮新增美瞳

列表卡片显示：

-   图片
-   品牌、名称
-   周期名称
-   颜色方案
-   状态
-   备注摘要

提供空状态、加载状态和错误状态。

## 4. 美瞳数据与详情功能

### 4.1 美瞳基础字段

美瞳详情必须支持以下业务字段：

  字段                          说明
  ----------------------------- -------------------------------------------
  id                            主键
  brand                         品牌
  name                          美瞳名称
  cycle_id                      周期 ID，关联周期表
  Color_scheme / color_scheme   颜色方案，代码中统一采用 `colorScheme`
  images                        多张图片，通过独立图片表管理
  Lens_Specs / lens_specs       镜片参数 JSON，代码中统一采用 `lensSpecs`
  status                        数据库存储状态
  note                          备注

为支持到期计算，还需要增加：

-   `opened_at`：开封日期
-   `package_expiry_date`：包装有效期
-   `discarded_at`：丢弃日期
-   `created_at`、`updated_at`

### 4.2 Lens_Specs JSON 结构

字段名称必须保持以下语义和拼写，不要随意改名：

``` json
{
  "Lens_diameter": 14.2,
  "Colored_diameter": 13.2,
  "Moisture_content": 48,
  "Base_arc": 8.6,
  "Left_eye_prescription": -3.25,
  "right_eye_prescription": -3.50
}
```

要求：

-   SQLite 中使用 TEXT 保存 JSON。
-   读取和写入时进行 JSON 编解码与基本校验。
-   数值字段使用数值类型；含水量保存为数值百分比，例如 `48`，UI 显示为
    `48%`。
-   字段允许为空，不能因为某项参数未填写而导致整个美瞳无法保存。
-   UI 使用清晰的表单展示，不要求用户直接编辑原始 JSON 字符串。

### 4.3 多图片管理

-   一副美瞳支持多张图片。
-   支持从相册选择图片；如果平台支持，也可支持拍照。
-   支持图片预览、删除和排序。
-   图片文件复制到 App 持久化目录，不要只保存临时缓存路径。
-   SQLite 只保存图片路径和排序信息，不直接把大图片二进制写入数据库。
-   删除美瞳时，按明确的文件清理策略处理关联图片，避免误删其他记录的文件。

### 4.4 状态规则

数据库存储状态建议采用：

  数据库存储值   UI 展示
  -------------- -----------------
  `unopened`     未开封
  `opened`       使用中 / 已开封
  `discarded`    已丢弃

**已过期（expired）由业务层根据日期动态计算，不作为普通持久化状态写入。**

规则：

-   `unopened`：未开封；若包装有效期已过，则计算为已过期。
-   `opened`：已开封；根据开封日期和周期计算使用到期日。
-   `discarded`：用户主动丢弃，不参与使用中、未开封和已过期统计。
-   已开封记录如果包装有效期和使用周期到期日都存在，以较早的日期作为最终到期日。
-   未填写包装有效期时，不得凭空推断包装有效期；仍可根据开封周期计算。

### 4.5 开封操作

详情页提供「开始使用 / 标记开封」操作：

1.  用户确认开封日期（默认当天）。
2.  保存 `opened_at`。
3.  将状态更新为 `opened`。
4.  根据 `cycle_id` 计算到期日。
5.  重新安排该美瞳相关的本地通知。

详情页还应提供编辑、保存、丢弃等操作，并对删除或丢弃操作进行确认。

## 5. 周期表与到期计算

### 5.1 周期表

表名：`lens_cycles`

字段：

  字段          类型      说明
  ------------- --------- -----------------------------------
  id            INTEGER   主键
  cycle_name    TEXT      周期名称
  cycle_unit    TEXT      `day` / `week` / `month` / `year`
  cycle_value   INTEGER   周期数值
  is_builtin    INTEGER   是否系统预设
  sort_order    INTEGER   排序
  created_at    TEXT      创建时间

初始化预设数据：

  cycle_name   cycle_unit     cycle_value
  ------------ ------------ -------------
  日抛         day                      1
  双周抛       week                     2
  月抛         month                    1
  季抛         month                    3
  半年抛       month                    6
  年抛         year                     1

支持用户自定义周期，例如 10 天、3 周、2 个月、18
个月。自定义周期直接新增周期记录，不通过硬编码增加条件分支。

内置周期不能被普通删除；如果某个周期已被美瞳记录引用，不允许直接删除。修改或删除自定义周期时也要考虑外键约束。

### 5.2 日期计算规则

-   日、周按自然日计算。
-   月、年按自然月和自然年计算，不得把一个月固定当成 30
    天，也不得把一年固定当成 365 天。
-   月末或闰年没有对应日期时，采用目标月份最后一天截断。例如 1 月 31
    日加一个月，得到 2 月最后一天。
-   日期按本地日历日期处理，避免 UTC 转换造成日期偏移。
-   将「到期日」定义为建议停止使用 /
    更换的日期；当天及之后显示为已过期，即 `today >= expiryDate`。
-   提前提醒日期为 `expiryDate - advanceDays`。
-   到期日、提醒日和剩余天数的边界规则必须集中在一个日期计算服务中，并编写单元测试。

请为以下情况编写测试：

-   日抛、双周抛、月抛、季抛、半年抛、年抛
-   月末加月
-   闰年 2 月 29 日加年
-   到期当天
-   提前提醒当天
-   包装有效期早于使用周期到期日
-   未填写包装有效期
-   已丢弃记录

## 6. 我的页面功能

我的页面采用设置列表风格，至少包含：

1.  系统通知
2.  提醒设置
3.  自动更新
4.  GitHub 镜像加速
5.  当前版本

### 6.1 系统通知

-   显示系统通知权限状态。
-   提供应用内通知总开关。
-   用户关闭应用内通知后，不再安排本应用的提醒。
-   如果系统权限被关闭，明确提示用户前往系统设置开启。
-   不要把数据库中的开关值误认为系统已经授予通知权限。
-   可展示近期通知记录（如果已实现通知记录表）。

### 6.2 提醒设置

提醒设置页面分为三个独立卡片区域。

#### A. 美瞳到期提醒

-   开关：开启 / 关闭
-   提前天数：1 天、3 天、7 天
-   提醒时间：默认 09:00，可调整
-   默认开启，提前 3 天，09:00

#### B. 护理液更换提醒

-   开关：开启 / 关闭
-   更换频率：每天、每 2 天、每 3 天、每周、自定义
-   自定义频率使用天数输入
-   提醒时间：默认 09:00，可调整
-   显示上次更换日期和下次更换日期
-   提供「已更换护理液」操作

点击「已更换护理液」后，在一个数据库事务中：

1.  写入更换历史记录。
2.  更新 `last_changed_date`。
3.  根据更换间隔计算 `next_changed_date`。
4.  更新或重新安排本地通知。

#### C. 护理液到期提醒

-   开关：开启 / 关闭
-   提前天数：至少支持 1 天、3 天、7 天
-   提醒时间：默认 09:00，可调整
-   护理液到期日期由护理液包装有效期和开封后有效天数计算。

护理液更换提醒与护理液本身到期提醒是两项不同业务，必须独立配置、独立计算和独立通知。

### 6.3 护理液信息

为支持护理液到期提醒，提供最小可用的护理液信息维护能力：

-   品牌
-   名称
-   开封日期
-   包装有效期
-   开封后有效天数
-   是否当前使用
-   备注

到期日计算：

-   有包装有效期时，使用包装有效期。
-   有开封日期和开封后有效天数时，计算开封后到期日。
-   两个日期都存在时，取较早日期。
-   相关日期缺失时，不得编造日期；界面应提示用户补充信息。

## 7. SQLite + Drift 数据库设计

使用 Drift 管理所有本地业务表，启用 SQLite
外键约束，建立必要索引，并实现数据库版本迁移。

建议首期包含以下 10 张表：

### 7.1 `lens_cycles`：美瞳周期表

字段见第 5 节。

### 7.2 `lenses`：美瞳详情表

建议字段：

-   `id`
-   `brand`
-   `name`
-   `cycle_id`（外键关联 `lens_cycles.id`，删除策略 `RESTRICT`）
-   `color_scheme`
-   `lens_specs`（JSON TEXT）
-   `status`
-   `opened_at`
-   `package_expiry_date`
-   `discarded_at`
-   `note`
-   `created_at`
-   `updated_at`

### 7.3 `lens_images`：美瞳图片表

字段：

-   `id`
-   `lens_id`（外键关联 `lenses.id`，删除美瞳时级联删除图片记录）
-   `image_path`
-   `sort_order`
-   `created_at`

### 7.4 `lens_expiry_reminder_settings`：美瞳到期提醒设置表

字段：

-   `id`（单例配置，默认使用 1）
-   `is_active`
-   `advance_days`
-   `reminder_time`
-   `updated_at`

### 7.5 `care_solution_change_reminders`：护理液更换提醒表

字段：

-   `id`（首期可采用单例配置，默认使用 1）
-   `is_active`
-   `frequency`
-   `interval_days`
-   `reminder_time`
-   `last_changed_date`
-   `next_changed_date`
-   `updated_at`

`frequency` 使用稳定的枚举字符串，例如
`daily`、`every_2_days`、`every_3_days`、`weekly`、`custom`；实际计算以
`interval_days` 为准。

### 7.6 `care_solution_change_logs`：护理液更换历史表

字段：

-   `id`
-   `reminder_id`
-   `changed_at`
-   `note`

### 7.7 `care_solution_bottles`：护理液信息表

字段：

-   `id`
-   `brand`
-   `name`
-   `opened_at`
-   `package_expiry_date`
-   `after_open_valid_days`
-   `is_current`
-   `note`
-   `created_at`
-   `updated_at`

### 7.8 `care_solution_expiry_settings`：护理液到期提醒设置表

字段：

-   `id`（单例配置，默认使用 1）
-   `is_active`
-   `advance_days`
-   `reminder_time`
-   `updated_at`

### 7.9 `app_settings`：应用设置表

采用 Key-Value 结构：

-   `key`：TEXT 主键
-   `value`：TEXT
-   `updated_at`

至少保存：

-   `system_notifications_enabled`
-   `auto_update_enabled`
-   `github_mirror_mode`（`official` / `mirror` / `auto`）
-   `update_channel`（默认 `stable`）
-   `last_update_check_at`

系统真实通知权限必须从操作系统读取，不能只依赖此表。

### 7.10 `notification_logs`：通知记录表

字段：

-   `id`
-   `notification_key`（唯一约束，用于去重）
-   `target_type`
-   `target_id`
-   `scheduled_date`
-   `sent_at`
-   `status`

用于记录通知计划和发送情况，避免同一业务在同一日期重复安排或重复触发。

### 7.11 数据库实现要求

-   每张表使用独立 Drift Table 定义。
-   使用 DAO 或 Repository 封装数据库操作。
-   为外键字段、日期查询字段和常用筛选字段建立索引。
-   使用事务处理跨表写入，例如保存美瞳和图片。
-   处理图片记录与文件系统之间的一致性。
-   提供初始化周期数据和默认提醒配置。
-   实现 `schemaVersion` 和迁移策略。
-   不允许通过删除数据库或清空数据的方式解决迁移问题。
-   数据库查询应支持响应式更新，让首页统计和列表在数据变化后自动刷新。

## 8. 本地通知实现

使用适合 Flutter 的本地通知方案，并确认所选插件与目标平台兼容。

要求：

1.  首次启用提醒时再请求通知权限，不要 App 一启动就强制弹权限框。
2.  美瞳新增、编辑、开封、丢弃或删除后，重新计算相关提醒。
3.  护理液更换日期、间隔或提醒时间改变后，重新安排更换提醒。
4.  护理液有效期或开封信息改变后，重新安排到期提醒。
5.  应用启动和从后台恢复时，重新校验未来提醒。
6.  关闭某一类提醒时，取消该类别对应的待触发通知。
7.  使用稳定的通知 ID 或唯一业务键防止重复通知。
8.  处理通知权限被系统撤销、设备重启和时区变化等情况。
9.  对操作系统后台调度限制保持诚实，不要承诺平台无法保证的精确触发时间。

通知标题和正文使用清晰中文，例如：

-   「美瞳即将到期」：Olens Scandi Hazel 将于 3 天后到期。
-   「请更换护理液」：今天是计划更换护理液的日期。
-   「护理液即将到期」：当前护理液即将到期，请及时检查。

## 9. 自动更新与 GitHub 镜像加速

将更新功能独立封装为 `updater` 模块，不要耦合到美瞳业务代码。

### 9.1 更新流程

1.  请求 GitHub Releases API。
2.  获取最新 Release 的版本号、更新说明、发布时间和安装包 Asset。
3.  比较当前版本与最新版本。
4.  根据平台选择对应安装包。
5.  根据用户设置选择官方源、镜像源或自动模式。
6.  下载时展示进度、速度或失败原因（能可靠获取时再展示）。
7.  下载完成后校验 SHA-256。
8.  校验通过后，进入平台允许的安装流程。
9.  失败时展示明确错误，并允许重试或切换下载源。

### 9.2 镜像加速

-   支持官方源、镜像源、自动模式。
-   自动模式下镜像失败应回退官方源。
-   镜像地址采用可信、可配置的白名单。
-   不要臆造镜像服务地址或 URL 转换规则；具体镜像服务应通过配置提供。
-   不得把 GitHub Token 或其他密钥写入客户端代码。
-   下载源切换不能绕过 SHA-256 校验。

### 9.3 平台限制

-   Android：可下载 APK，校验后调用系统安装程序，由用户确认安装；按
    Android 版本处理安装未知应用权限。
-   iOS：普通 App 不得实现从 GitHub 下载 IPA 并在 App
    内自行安装更新。iOS 更新应引导至 App Store、TestFlight
    或项目实际采用的合规分发渠道。
-   如果当前项目只支持 Android，先完成 Android
    更新流程，同时把平台接口抽象出来，不要伪造 iOS 自动安装能力。

### 9.4 缺失配置

GitHub 仓库 owner、repo、Release Asset 命名规则和镜像地址如果尚未提供：

-   通过配置文件或常量集中管理。
-   使用明确的占位配置。
-   在 README 中列出需要用户填写的值。
-   不要自行猜测仓库地址或镜像地址。
